# proxy-unifi

Запустите прокси-клиент без графического интерфейса прямо на шлюзе UniFi Cloud
Gateway и направляйте в него трафик из штатного интерфейса UniFi
(**Policy Engine → Policy Table**).

proxy-unifi включает **три ядра** — [xray-core](https://github.com/XTLS/Xray-core),
[sing-box](https://github.com/SagerNet/sing-box) и закреплённое userspace-ядро с
[поддержкой AmneziaWG](https://github.com/amnezia-vpn/amnezia-box). Подходящее ядро
выбирается для импортированных ссылок и сохранённых AWG-профилей. Все три завершают
**один и тот же** туннель WireGuard, поэтому в UniFi достаточно **одной** записи VPN Client.

Шлюзы UniFi не имеют встроенной поддержки исходящего прокси и не умеют подключаться к серверам по ссылкам прокси-протоколов (`vless://`, `hysteria2://`, ...).
proxy-unifi закрывает этот пробел **без** изменения пакетов UniFi OS: он представляет
прокси для UniFi как штатно поддерживаемый **WireGuard VPN Client**, который контроллер
уже умеет маршрутизировать. Решение работает без графического интерфейса, управляется
только по SSH (без веб-интерфейса) и сохраняется при перезагрузках и обновлениях
прошивки благодаря [unifi-common](https://github.com/unifi-utilities/unifi-common).

## Быстрый старт

Подключитесь к шлюзу по SSH под пользователем `root` и выполните:

```sh
curl -fsSL https://raw.githubusercontent.com/palmbeachpete9/proxy-unifi/experimental/install.sh | sh
```

После завершения установки запустите `proxy`, чтобы открыть меню управления:

1. **Импортируйте подключение** — выберите в меню отдельную серверную ссылку
   (`vless://`, `vmess://`, `trojan://`, `ss://`, `hysteria2://` или `tuic://`),
   HTTPS-подписку, JSON-профиль Xray либо профиль AmneziaWG.

2. **Скопируйте показанную конфигурацию WireGuard VPN Client** — создайте файл `.conf` на своём компьютере и загрузите его в:

   `unifi.ui.com → Ваш шлюз → Settings → VPN → VPN Client → Create New → WireGuard`

3. Наконец, с помощью **Policy Engine** создайте любые нужные маршруты трафика, используя штатные возможности Ubiquiti — маршрутизацию по VLAN / устройству / IP / домену / региону.

Созданный файл `.conf` и конфигурация WireGuard в Ubiquiti сохраняются на всё время работы скрипта. Смена прокси-ссылок или протоколов **не** меняет их, что упрощает обслуживание.

## Как это работает

```
  ┌─────────────────────────── UniFi Cloud Gateway ────────────────────────────┐
  │  клиент VLAN ─▶ маршрут Policy Table ─▶ WireGuard VPN Client (UniFi)       │
  │                              │ зашифрованный WireGuard поверх loopback     │
  │                              ▼  udp 127.0.0.1:51821                        │
  │      xray-core  ИЛИ  sing-box  ИЛИ  ядро AmneziaWG (вход WireGuard)        │
  │                              │  завершает туннель и маршрутизирует трафик  │
  │                              ▼  выбранный прокси- или AWG-исход            │
  └──────────────────────────────┼─────────────────────────────────────────────┘
                                 ▼  в обычный WAN
                              Ваш прокси / VPN-сервер ──▶ Интернет
```

Встроенный в шлюз WireGuard VPN Client выполняет настоящее рукопожатие WireGuard с
активным ядром по loopback. Ядро завершает этот внутренний туннель и направляет
трафик через выбранный прокси- или AWG-исход. В режимах прокси-ссылок удалённый
сервер WireGuard не требуется; в режиме AWG ядро подключается к удалённому пиру
AmneziaWG из выбранного профиля.

## Kernel WireGuard ingress (Xray и sing-box)

Для ссылок Xray и sing-box и JSON-профилей Xray WireGuard от UniFi VPN Client по
умолчанию завершает ядро Linux шлюза, а не прокси-ядро. Собственный WireGuard Xray расшифровывает
трафик в userspace по одному пакету: на UCG-Ultra это держало туннель около
35 Мбит/с, хотя сам прокси-исход давал ~350 Мбит/с. На том же шлюзе путь через
ядро показал ~180 Мбит/с при вдвое меньшей загрузке CPU.

Устройство WireGuard в ядре использует тот же порт, ключи и MTU, поэтому в UniFi
VPN Client ничего менять не нужно. Оно находится в отдельном сетевом пространстве
имён; расшифрованный трафик выходит через пару veth, а TPROXY передаёт каждое
TCP- и UDP-соединение прокси-ядру, которое маршрутизирует его как раньше (тот же
тег inbound; у Xray сохраняется sniffing). sing-box запускает копию своего конфига,
в которой вместо WireGuard endpoint стоит inbound `tproxy`. Профили AmneziaWG
остаются на собственном WireGuard.

- **Откат:** если какой-либо шаг настройки не удался или ядро не поднялось на
  этом пути (не прошло проверку после перезапуска или трижды подряд завершилось
  с ошибкой), сервис использует собственный WireGuard прокси-ядра. **Check status**
  в меню показывает текущий путь и причину; **Restart** снова пробует путь через ядро.
- **Переключение:** `proxy` → настройки WireGuard → Ingress (`kernel` или `userspace`).
- **Перезапись правил:** если контроллер UniFi перезапишет правила firewall или
  маршрутизации, таймер-страж восстановит их в течение 30 секунд.
- **UDP-ответы с портов, которые слушает шлюз:** прокси-ядро отвечает на прозрачный UDP
  с адреса и порта удалённой стороны, а это невозможно для портов, занятых самим
  шлюзом (например, STUN UniFi на 3478). Такие ответы теряются; **Check status**
  перечисляет эти порты. TCP это не затрагивает.
- **Привилегии:** только в этом режиме ядро получает `CAP_NET_RAW`, необходимую
  для прозрачных сокетов, и `CAP_NET_BIND_SERVICE`, чтобы отвечать на UDP с
  удалённых портов ниже 1024 (DNS, QUIC).
- **Частные адреса:** как и с WireGuard inbound Xray, прямые маршруты (freedom)
  не пропускают клиентов туннеля к частным и loopback-адресам. В конфигах sing-box
  прямых маршрутов нет: всё идёт в прокси.
- **LAN route (по умолчанию включено):** в меню настроек WireGuard. Трафик LAN, который маршрут Policy Table отправляет
  в этот VPN Client, маршрутизируется во вторую пару veth proxy-unifi вместо
  шифрования и
  попадает в прокси-ядро без обоих проходов WireGuard, пакетами полного размера. UniFi всё равно сначала
  обрабатывает его: метки, NAT (перехват DNS, hotspot), свои таблицы маршрутизации
  и файрвол FORWARD. Файрвол видит выходным интерфейсом `pu-lr0`, а не `wgclt`,
  поэтому правила для интерфейса зоны VPN не срабатывают; правила по адресам или
  по интерфейсу LAN — срабатывают. Из этой пары обратно пропускаются только ответы
  на соединения, которые шлюз сам туда переслал, и о них, как об ответах из
  `wgclt`, решает цепочка FORWARD UniFi (включая её списки угроз). Трафик, который сам шлюз
  отправляет через VPN Client (например, DNS-форвардер UniFi для него), тоже идёт
  через пару, и к шлюзу из неё попадают только ответы. **Check status** показывает `lan route` и сколько TCP-соединений
  пропустил файрвол UniFi; `blocked` означает, что режим невозможен из-за строгой
  проверки обратного пути (`rp_filter=1`).
- **Замер:** третья строка **Speed test** проверяет весь туннель через VPN Client
  самого шлюза.
- **Установка более старой версии:** версии без этого режима не умеют его снимать,
  и он продолжит занимать порт WireGuard. Сначала выполните
  `systemctl stop proxy-unifi` (или перезагрузите шлюз после установки).

## Совместимость

Пакет совместим с UniFi OS 4.x и новее и проверен на следующих устройствах UniFi:
| Модель | Код |
|---|---|
| UniFi Cloud Gateway Ultra | `UCG-Ultra` |
| UniFi Cloud Gateway Max | `UCG-Max` |
| UniFi Cloud Gateway Fiber | `UCG-Fiber` |
| UniFi Dream Router | `UDR` |
| UniFi Dream Router 7 | `UDR7` |
| UniFi Dream Machine | `UDM` |
| UniFi Dream Machine Pro | `UDM-Pro` |
| UniFi Dream Machine SE | `UDM-SE` |
| UniFi Dream Machine Pro Max | `UDM-Pro-Max` |
| UniFi Express | `UX` |
| UniFi Express 7 | `UX7` |
| UniFi Enterprise Fortress Gateway | `EFG` |

> **Примечание:** Некоторые обновления UniFi OS (например, UniFi OS 5.1.12 с рядом исправлений CVE) могут полностью стереть скрипт и его данные из встроенной памяти.
> Сохраните свою прокси-ссылку на такой случай и переустановите proxy-unifi.

Ядро прокси выбирается автоматически по импортированной ссылке:

| Протокол | Ядро |
|---|---|
| VLESS | xray-core |
| VMess | xray-core |
| Trojan | xray-core |
| Shadowsocks — обычный / классический AEAD | xray-core |
| Shadowsocks 2022 — стандартные ключи фиксированной длины | sing-box |
| Shadowsocks 2022 AES-128 — 32-байтный ключ совместимости Xray | xray-core |
| Shadowsocks + obfs-local / simple-obfs | sing-box |
| Shadowsocks + v2ray-plugin | sing-box |
| Hysteria2 | sing-box |
| TUIC | sing-box |
| Конфигурация AmneziaWG 1.5 / 2.0 / 3.0 / 3.1 | ядро AmneziaWG |

Одновременно работает только одно ядро. Все три используют **одни и те же** ключи и порт
WireGuard, поэтому единственная запись VPN Client в UniFi работает независимо от того,
какое ядро активно.

> **Примечание:** xray слушает порт WireGuard на loopback (`127.0.0.1:51821`).
> У sing-box и ядра AmneziaWG нет опции выбора адреса прослушивания внутреннего
> WireGuard-эндпойнта, поэтому они слушают на всех
> интерфейсах — но proxy-unifi добавляет правило `iptables`/`ip6tables`, которое
> отбрасывает все не-loopback пакеты к этому порту, делая его недоступным из
> локальной сети и из интернета. Защита в несколько слоёв: порт закрыт файрволом
> до loopback **и** WireGuard отвечает только одному настроенному ключу-пиру.

Распространённые дополнительные параметры ссылок учитываются, если ядро их
поддерживает: `tfo` / `fastopen` (TCP Fast Open; не используется в Hysteria2 и TUIC,
работающих поверх QUIC), смена портов Hysteria2 (`mport`, `hop-interval` или список
портов вида `host:443,20000-30000`), `upmbps` / `downmbps`, `obfs=none`, `disable_sni`
для TUIC и `uot` для Shadowsocks. Отпечаток `fp` в Hysteria2 и TUIC игнорируется:
sing-box не может применить его поверх QUIC. Параметры, меняющие безопасность
(например, `insecure=1` или `pinSHA256` в Hysteria2), по-прежнему отклоняются, а список
подписки помечает такие узлы как неподдерживаемые с указанием причины.

## Shadowsocks 2022

SS2022 импортируется через существующие функции одиночных ссылок и подписок;
отдельное меню профилей и вторая запись VPN Client в UniFi не нужны. В каталоге
такие узлы помечаются как `ss2022`, а в разделе **Статус** для активного узла
отображается `Shadowsocks 2022`.

Поддерживаемые стандартные методы:

- `2022-blake3-aes-128-gcm` — 16-байтный PSK в base64
- `2022-blake3-aes-256-gcm` — 32-байтный PSK в base64
- `2022-blake3-chacha20-poly1305` — 32-байтный PSK в base64

Однопользовательские ключи поддерживаются для всех трёх методов. Разделённые
двоеточиями цепочки расширяемой идентификации
(`ключ-реле:ключ-сервера:ключ-пользователя`, до 16 ключей) поддерживаются для двух
методов AES-GCM; эта многопользовательская конструкция несовместима с ChaCha20.
Синтаксис и длина ключей проверяются до загрузки ядра и до изменения активного
туннеля. Стандартные ссылки работают через sing-box. Старый специфичный для Xray
32-байтный ключ AES-128 сохранён через xray-core во избежание регрессий; в подписке
такая строка получает предупреждение о режиме совместимости.

Для защиты SS2022 от повторного воспроизведения часы клиента и сервера должны быть
достаточно точно синхронизированы. Мультиплексирование и UDP-over-TCP не включаются
скрыто: сервер провайдера должен поддерживать их явно, иначе корректная ссылка
перестанет работать. Обычная передача TCP и UDP остаётся включённой по умолчанию.

## Подписки и JSON-пулы

Меню «Подписки» хранит до 20 HTTPS-подписок одновременно, у каждой свой номер,
имя (название от провайдера или домен ссылки; его можно изменить) и, если
провайдеру нужен, свой User-Agent. Чтобы выбрать активный узел, сначала
выбирается подписка, затем узел (при одной подписке первый шаг пропускается).
Подписки содержат обычный или закодированный в base64 список ссылок, а также
клиентские JSON-профили Xray с балансировщиками.
Имена узлов сохраняются в Unicode, включая кириллицу и эмодзи. Выбранный узел
проходит тот же проверяемый путь импорта, что и отдельная прокси-ссылка.
Форматы Clash YAML, SIP008, sing-box JSON, WireGuard, AnyTLS, Naive и SSH пока
не разбираются.

При установке создаётся случайный постоянный UUID устройства. Он отправляется
источнику подписки в заголовке `x-hwid`, но не передаётся при перенаправлении на
другой домен. User-Agent по умолчанию — `Happ/2.0`; его можно изменить в меню
«Подписки» для всех подписок или для одной. Постоянный таймер systemd в фоне
обновляет все подписки с заданным интервалом; если один провайдер недоступен,
его узлы сохраняются, а остальные подписки обновляются, и загрузка никогда не
блокирует меню и наблюдатель резервного пула. После обновления выбранный узел
находится по точному содержимому, а если оно изменилось — по имени, протоколу и
серверу. Если провайдер перенёс узел на другой сервер, его место занимает узел с
тем же именем и протоколом, а из нескольких таких — тот, что стоит на той же
позиции в списке. Если подходящего нет, активный туннель остаётся без изменений.

JSON провайдера не запускается без проверки. proxy-unifi проверяет адреса,
ссылки маршрутизации, балансировщики, observatory, DNS и лимиты ресурсов;
удаляет входящие слушатели и управляющие интерфейсы провайдера; затем добавляет
собственный вход WireGuard. Исходящие подключения, правила маршрутизации,
алгоритмы балансировки, проверки доступности и fallback-теги провайдера
сохраняются. Профиль, который нельзя безопасно адаптировать, отклоняется до
запуска xray-core.

Правила, зависящие от источника, пользователя или локального адреса и порта
исходного входа провайдера, отклоняются, если относятся к сохраняемому входу.
Это касается `source`, `sourceIP`, `sourcePort`, `user`, `localIP` и `localPort`.
Правила только для удаляемых входов отбрасываются. Webhook в маршрутизации не
поддерживается: он может отправлять метаданные соединений отдельным HTTP-клиентом,
минуя исходящие подключения профиля.

## Резервный пул

Пункт 3 главного меню настраивает пул из 2-10 узлов из любых ваших подписок в
порядке приоритета. Пока резерв включён, наблюдатель с заданным интервалом
проверяет активный узел через туннель. Если узел не проходит заданное число
проверок подряд, он считается недоступным, и туннель переходит на следующий по
приоритету узел, который отвечает прямо сейчас. Если включён возврат к более
приоритетному узлу, туннель возвращается на него, когда тот пройдёт заданное
число проверок подряд. Если не отвечает ни один узел пула (например, пропал
интернет), наблюдатель проверяет по одному узлу за интервал, а не все сразу,
чтобы не нагружать процессор шлюза.

Мастер спрашивает число узлов, каждый узел (подписка, затем узел), их порядок и
интервалы:

| Набор | Проверка каждые | Недоступен после | Снова доступен после |
|---|---|---|---|
| Быстрый | 10 с | 3 неудачных проверок (~30 с) | 3 удачных проверок |
| Сбалансированный (по умолчанию) | 20 с | 3 неудачных проверок (~1 мин) | 5 удачных проверок |
| Спокойный | 60 с | 3 неудачных проверок (~3 мин) | 5 удачных проверок |

В своём наборе каждое значение (и секунды на проверку) задаётся вручную.
Переключение применяет узел так же, как ручной выбор, поэтому открытые
соединения сбрасываются: для узлов с kernel ingress это около 1-3 с, а узел на
собственном WireGuard ядра заставляет VPN-клиент UniFi переподключиться, до ~15 с. Ручной выбор узла (ссылка, узел подписки, JSON- или AmneziaWG-профиль)
сначала спрашивает подтверждение, затем выключает резерв; пул сохраняется. Если
проблема между UniFi и ядром, а не в узле, наблюдатель не переключает узел, и
**Check status** сообщает об этом. Каждое переключение пишется в журнал
(**View logs**) и показывается в меню как «Last switch».

## Профили AmneziaWG

Второй блок меню управляет отдельными клиентскими конфигурациями AmneziaWG 1.5,
2.0, 3.0 и 3.1. Выберите **Создать новый профиль**, задайте отображаемое имя, вставьте
конфигурацию в редактор и сохраните её (в `nano`: `Ctrl+X`, `Y`, `Enter`). Сохранённые
профили можно просматривать, выбирать и активировать, редактировать,
переименовывать и удалять; `*` отмечает активный профиль. Кириллица, CJK и эмодзи
сохраняются, а для ограниченных SSH-терминалов UniFi применяется только
отображаемая безопасная замена. Редактор — `nano`, если он есть на шлюзе, иначе
`vi`, который входит в UniFi OS; меню подсказывает, как в нём сохранить.

AWG полностью работает в userspace: не создаёт интерфейс ядра, не меняет
маршруты шлюза, не требует `/dev/net/tun` и не заменяет постоянный WireGuard-клиент
UniFi. Поэтому при выборе AWG-профиля ничего менять в UniFi UI не нужно. Ядро AWG
загружается при первой активации; версия закреплена релизом проекта, а архив
проверяется по встроенному в proxy-unifi SHA-256 для соответствующей архитектуры.

Импортируются поля обфускации `Jc`, `Jmin`, `Jmax`, `S1-S4`, `H1-H4` и `I1-I5`,
включая диапазоны заголовков AWG 2.0 и CPS-шаблоны пакетов, а также поля AWG 3.0
`HeaderProtectionKey`, `ContentPaddingAddition`, `RekeyAfterTime`, `RekeyTimeout`,
`RejectAfterTime`, `KeepaliveTimeout`, `MaxHandshakeAttempts` и флаги AWG 3.1
`RandomTrailers` и `DisableCookies`. Параметры AWG 3.x должны совпадать с сервером.
Сервер с `HeaderProtectionKey` принимает только клиентов AWG 3.x, а защита
заголовков требует `S1-S4` не меньше 12. Для диапазона `PersistentKeepalive`,
например `20-30`, используется нижняя граница; переключатель пира модуля ядра
`AdvancedSecurity = on` принимается. Поддерживаются несколько
пиров, IPv4/IPv6, preshared keys и keepalive. Опасные хуки и команды маршрутизации
`wg-quick` отклоняются. Клиентский `ListenPort` сохраняется в исходном профиле, но
не переносится в рабочую конфигурацию, чтобы не открывать лишний UDP-порт. DNS из
профиля показывается справочно; UniFi получает глобальный DNS из раздела
**Настройки WireGuard**.

## Использование

Запустите `proxy`: всё находится в его меню.

- **Подключения:** отдельная ссылка, подписки, резервный пул, профили AmneziaWG
  и JSON-профили Xray; текущий сервер и конфигурация.
- **Сторона UniFi:** конфигурация WireGuard VPN Client, новые ключи и настройки
  WireGuard (порт, MTU, DNS, ingress, LAN route, keepalive, уровень журнала).
- **Проверки:** проверка связи и её протокол, а также **Speed test**: WAN напрямую,
  активный прокси отдельно (без WireGuard) и весь туннель через VPN Client шлюза,
  с загрузкой CPU шлюза и ядра.
- **Служба:** запуск, остановка, перезапуск, состояние, журналы и автозапуск.
- **Updates:** proxy-unifi, прокси-ядра, гео-файлы, автоматические обновления и
  версии (см. [Обновление](#обновление)). Затем **Uninstall**.

## Примечания

- **Управление только по SSH:** нет ни веб-интерфейса, ни управляющего порта,
  доступного из локальной сети, — управление выполняется по SSH командой `proxy`.
- **Loopback-эндпойнт:** WireGuard VPN Client в UniFi указывает на `127.0.0.1:51821`.
  Пользовательский адрес `WG_LISTEN` поддерживается для ссылок xray-core и
  JSON-пулов. sing-box и ядро AmneziaWG не умеют привязывать этот вход к заданному
  адресу, поэтому для них proxy-unifi требует loopback-настройку и не запускает
  службу, если защитное правило файрвола установить не удалось.
- **MTU** по умолчанию `1340` (измените через главное меню, если зависают большие
  передачи); **DNS** по умолчанию `8.8.8.8`.
- **Разделение привилегий:** прокси-ядра работают от отдельного пользователя
  `proxy-unifi` в усиленной службе systemd. Импорт и обновление проверяются до
  атомарного изменения состояния; неудачный запуск восстанавливает прошлое
  рабочее состояние.
- **Целостность ядер:** xray-core не устанавливается ниже содержащего исправление
  безопасности `v26.7.11`; для этого релиза и ядра AWG используются встроенные
  хэши для каждой архитектуры. Более новые Xray должны совпасть с digest GitHub
  и sidecar-контрольной суммой Xray. sing-box закреплён на `v1.13.21` (1.14.3 не
  открывает порт WireGuard на Dream Router 7) и должен совпасть с digest GitHub.

## Сохранение данных

Все данные хранятся в **`/data/proxy-unifi`**, который UniFi OS сохраняет при
перезагрузках и большинстве обновлений прошивки. Хук загрузки
`/data/on_boot.d/15-proxy-unifi.sh` при каждой загрузке заново создаёт команду
`proxy` и службу systemd (с правильным ядром).

## Обновление

Пункт меню **Updates** обновляет proxy-unifi, прокси-ядра (Xray, sing-box,
AmneziaWG) и гео-файлы. **Update proxy-unifi now** устанавливает новейшую версию
установленной ветки (`main` или `experimental`), прошедшую тесты GitHub; если она
уже установлена, обновление ничего не делает.

**Автоматические обновления** выключены, пока вы не включите их там же. После
включения шлюз проверяет обновления ежедневно около 04:00: новая версия
proxy-unifi ставится через 24 часа после того, как прошла тесты (время заметить
плохую версию до того, как она попадёт на роутеры), затем обновляются ядра.
Обновление один раз перезапускает туннель на несколько секунд; в день без
новых версий ничего не перезапускается. **Check status** показывает текущую
версию и итог последнего автоматического обновления; подробности — в **View logs**.

Каждое обновление запускает установщик той версии, которую ставит: он проверяет
шлюз, сохраняет скрипты, ядра и службы и восстанавливает их, если не удался
любой шаг, включая проверку работоспособности туннеля. Повторный запуск команды
установки делает то же вручную:

```sh
curl -fsSL https://raw.githubusercontent.com/palmbeachpete9/proxy-unifi/experimental/install.sh | sh
```

При удалённой установке все файлы одного запуска привязываются к одному
неизменяемому коммиту GitHub. Архивы ядер и гео-файлы активируются только после
проверки опубликованных SHA-256; при ошибке обновления восстанавливаются прошлые
файлы и служба.

Повторный запуск установщика перезаписывает только `bin/` (скрипт + бинарники) и unit systemd. Ваши ключи WireGuard, добавленная прокси-ссылка, подписки, резервный пул, профили AmneziaWG и настройки клиента (DNS, MTU) сохраняются — WireGuard-клиент в UniFi продолжает работать без каких-либо изменений.

## Удаление

```sh
proxy            # меню → Uninstall
# или:
rm -rf /data/proxy-unifi   # также стирает ключи/конфигурацию
```
Затем удалите WireGuard VPN Client в интерфейсе UniFi.
